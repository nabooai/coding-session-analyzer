# Change checklist

> **STOP.** Do not declare any change "done" (not "PR is open", not "self-checks pass") until every
> applicable item below is green, however small the diff. Open this file first, before the source
> you are about to edit. It applies to people and to coding agents alike; the region between the
> session-start markers is injected into every Claude Code session by `.claude/hooks/inject_checklist.sh`.
>
> Legacy modules gate on their `__main__` self-check (`uv run python -m analyzer.<mod>` from `server/`);
> new code gates on pytest (`uv run pytest tests/`), plus MCP protocol hygiene. Branch names are plain
> short descriptions (no prefix convention).

**All commands run from `server/` unless noted.**

## What every change owes

1. **Lint and type-check clean on the changed files**: `ruff check` (server), `npm run check` (ui),
   `gofmt -l` and `go vet` (client). The `gh pr create` hook runs these and blocks when red.
2. **Tests for the change**, run and green (load the `code-tests` skill first).
3. **A visual walk** for any visible UI change: both themes, 390px, compared to the mock (`ui-visual-walk`).
4. **User simulations** when the task's protocol calls for them (`user-sims`), fixed and re-run.
5. **A fresh-context review** (`pr-code-review`) and **a PR body from the diff** (`pr-description`).
6. **A self-reflection** in the PR body, under a `Reflection` heading (`self-reflection`).
7. **The founder's review conventions**: no new env vars, no legacy shims, no narrative comments,
   asserts in tests, no em dashes in copy.

## ORM & DB conventions (the models ARE the schema; Alembic since 2026-09-05)

- **A schema change is a model change plus an autogenerated revision, reviewed by hand and committed
  with it.** There are no DDL strings: `store.SCHEMA`, `store.TELEMETRY_SCHEMA`, `orgs.SCHEMA` and the
  try/except `ALTER TABLE` lists are gone.

  ```bash
  cd server
  uv run alembic -c alembic.ini -n corpus revision --autogenerate -m "what changed"   # or -n telemetry / -n control
  uv run alembic -c alembic.ini -n corpus check          # no diff left between the models and a fresh file
  ```

  Autogenerate diffs the models against the throwaway file `alembic.ini` names, built by
  `alembic upgrade head`; never point it at a real `data/analyzer.db`. Read the revision before
  committing: a server default must be `sa.text("'value'")`, not a plain string, and an empty
  `upgrade()` means the diff found nothing. A DROP or a retype will not render at all (batch mode is
  off on purpose: its table copy loses CHECK constraints) and is written by hand. Traps and the rest:
  [`schema-migrations.md`](schema-migrations.md).
- **All DB access uses SQLAlchemy 2.0 typed models** (`Mapped[...]` / `mapped_column`) executed through
  the `analyzer/db.py` bridge (`db.run` / `db.run_many` on the caller's raw connection). **Never add a
  new raw `con.execute` site or a new raw-SQL module** — `tests/test_no_raw_sql.py` fails on one.
- **The only raw SQL that remains is a fixed set of DOCUMENTED CARVE-OUTS**, each with a written
  reason at the site and a pinned count in `tests/test_no_raw_sql.py`: the FTS5 `docs` virtual-table
  statements (MATCH/bm25/snippet), `store.sqlite_db`'s PRAGMAs and ATTACH, `build_fts`'s BEGIN
  IMMEDIATE body, `write_entity_stats`, `refresh_facts`' bi-temporal upsert, `store.ro_connect`'s
  ATTACH-denial authorizer, `ask.run_sql`'s model-authored planner SQL, `tracer.py`'s self-contained
  span writer, `migrations.py`'s version read plus the catch-up's `PRAGMA table_info`, and `orgs.py`'s
  two foreign read-only legacy reads. To add one you edit `ALLOWED` in that test and justify it in the
  commit. The `db.py` bridge is a PERMANENT seam, not scaffolding (see its docstring).
- **Settings live in a row, never in new `CSA_*` env vars.** A workspace field: `tenant.TenantConfigRow`
  + a `tenant._FIELDS` entry (scope, default, parse, check) + a corpus revision, read via
  `tenant.config(con)` / `tenant.get_config(db_path)`. A deployment field: `tenant.DeploymentSettingsRow`
  + a control revision, read via `tenant.deployment()`. `GET /api/config` and `csa.py org config`
  pick it up from `_FIELDS`. Read it per use, never into a module constant: a change applies with no restart.
- **New-table checklist:** add the typed model to `analyzer/models.py` (corpus), `models.telemetry`
  (telemetry) or `tenant.ControlBase` (control), autogenerate the revision for that environment, read
  it, and commit both. There is no parity list to update: `tests/test_migrations.py` compares the
  models to a freshly migrated file for all three environments, with a negative control.
- **One head per environment.** Two branches cutting a revision off the same head make
  `alembic upgrade head` fail at container boot on prod. Rebase and re-parent the later revision.
- **Three files, and which one a table belongs in.** SQLite allows exactly ONE writer per FILE, so the
  file split IS the concurrency design:
  * `analyzer.db` (corpus, attached as `main`) — everything a question is answered from. Written by
    ingest/compaction, read by serving.
  * `telemetry.db` (attached as `tel`, a sibling per org) — write-mostly records of what the system
    DID: `served`, `queries`, `spans`. Nothing here answers a question. A table belongs here if the
    serving path writes it on every request; put it anywhere else and an `ask` can queue behind ingest.
    Models carry `schema="tel"`; joins across the two files are ordinary SQL on the same connection.
  * `control.db` — the control plane (orgs, tokens), `orgs.py` only, never through `db.engine_for`.
- **A write holds the writer lock; do not compute while holding it.** Compute first (`fetchall`), then
  `BEGIN` → apply → commit, and make the FIRST statement in that block a write. Never `BEGIN IMMEDIATE`
  on a `store.sqlite_db` connection: IMMEDIATE locks every ATTACHED database, so it takes the telemetry
  writer too and undoes the file split (`tests/test_telemetry_split.py::test_build_fts_does_not_lock_the
  _telemetry_file` is the tripwire). `write_entity_stats` and `write_clusters` are the pattern. The
  scar: `write_entity_stats` computed inside its transaction and held the writer 81.8s per session on
  prod, which failed every concurrent write past `busy_timeout` (see its docstring). Prefer an
  incremental refresh scoped to what changed over a corpus-wide rebuild on an ingest path; corpus-wide
  passes belong in compaction (`csa.compact_org`; runs when the org's queue is idle, spacing
  `drain_loop.COMPACT_MIN`, starvation valve `COMPACT_MAX_MIN` — `drain_loop._compact_tick`).
- **Tests go in `server/tests/test_*.py` (pytest), never `__main__` blocks.** Modules that hold NO
  SQL (`dedup`, `llm`, `ingest`, `project`, `queue`, `extract`, `etl`, `harness`, `improve`,
  `incremental`, `drain_loop`, `memories`) keep their existing `__main__` self-checks permanently —
  they never "migrate", so those checks are not debt. `tracer.py` keeps its `__main__` too (carve-out).

## Per-change gates

- [ ] **Tests:** `uv run pytest tests/` green, and every touched legacy `analyzer/*.py` module's
      `__main__` self-check green: `uv run python -m analyzer.<module>`. New non-trivial code ships
      WITH tests (rule: code without its check is unfinished).
- [ ] **MCP stdout hygiene:** `mcp_server.py` (and anything it imports at tool-call time) must never
      `print()` — stdout is the JSON-RPC channel. Log to **stderr** only (`logging` is already wired).
      Quick audit: `grep -n "print(" mcp_server.py app.py` — hits must be CLI-only paths.
- [ ] **Schema changes ship as a revision:** the model edited, `alembic revision --autogenerate` run
      for that environment, the revision read by hand, `alembic check` clean, and
      `uv run pytest tests/test_migrations.py -q` green. Opening an existing `data/analyzer.db` must
      not error, rewrite a table, or duplicate rows.
- [ ] **Redaction gate:** any NEW text that flows into SQLite/FTS from raw session files passes
      through `analyzer.redact.redact()` first — same as transcripts.

## Bug-fix discipline — regression check first

1. Write the failing check first (extend the module's `__main__` self-check or a small `test_*.py`).
2. Run it against the un-fixed code — verify it FAILS with the bug's signature.
3. Fix, verify green. Then grep the same idiom across `analyzer/` — same-pattern bugs cluster.

## Wrapping up

- [ ] **Commit on a feature branch** (never straight to `master`), push with `git push -u origin <branch>`.
- [ ] **Run the `pr-description` skill** (`.claude/skills/pr-description/`) to write or refresh the PR
      body via `gh`; re-run after every push.
- [ ] **Fresh-context review before declaring done — run the `pr-code-review` skill**
      (`.claude/skills/pr-code-review/`) with a NEW agent/session so it reads the diff cold — the
      implementing session has a story for every finding that doesn't survive an independent read.
      That skill is ONE agent. Do not run Claude Code's built-in `code-review` skill above `medium`:
      at `high` it fans out to ~10 reviewer agents plus one verifier per candidate finding
      (≈50 agents and 40 minutes on PR #97, 2026-09-04), and the count is not configurable from
      this repo. `medium` or `low` only, and never a second pass on the same head.
- [ ] **Live E2E when the change touches recall/ask behaviour:** run the real path once
      (`uv run python csa.py recall <topic>` / the MCP `ask` tool) against the real `data/analyzer.db`,
      not just `:memory:` self-checks.

- [ ] **Write the reflection** in the PR body (the `self-reflection` skill, its `TEMPLATE.md`).
      Promote what recurs into this folder (`promote-lessons`).

> **STOP — final gate.** About to say "done"? Confirm: touched modules' self-checks green, no stdout
> prints on the MCP path, schema migration idempotent, redaction on new ingest surfaces, branch pushed,
> PR opened, fresh-context review done, reflection in the PR body. Missing any → you are **not done**.
